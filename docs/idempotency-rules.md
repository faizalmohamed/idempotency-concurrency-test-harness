# 🛡️ Idempotency Rules & Algorithm Specification

This document details the core rules, fingerprinting logic, database transaction boundaries, and status lifecycle implemented in **Phase 2** of the **Idempotency & Concurrency Test Harness**.

---

## 1. Idempotency Key Validation

The `Idempotency-Key` is passed via the HTTP request header to `/orders/v2`.

### Rules:
1. **Mandatory Header**: Protected endpoints (`/orders/v2`) require `Idempotency-Key`. Missing keys trigger an immediate **HTTP 400 Bad Request**.
2. **Data Type**: Must be a non-empty string.
3. **Length Constraint**: Enforces a maximum length of **128 characters**.
4. **Uniqueness Scope**: Represents a single logical transaction intent generated by the client (e.g. UUID v4).

---

## 2. Request Fingerprinting (SHA-256)

To detect payload tampering or key reuse with non-matching order parameters, every incoming payload is deterministically fingerprinted.

### Algorithm:
1. **Canonicalization**: Parse JSON payload and format using `json.dumps(payload, sort_keys=True, separators=(',', ':'))`. This ensures key order variations (e.g. `{"a": 1, "b": 2}` vs `{"b": 2, "a": 1}`) produce identical character sequences.
2. **SHA-256 Hash**: Hash the UTF-8 encoded canonical JSON string using `hashlib.sha256()`.
3. **Digest**: Store and compare the resulting 64-character hexadecimal digest.

---

## 3. Duplicate vs Conflict Detection

Given a stored idempotency record fingerprint ($FP_{stored}$) and an incoming request fingerprint ($FP_{incoming}$):

```
+-------------------------------------------------------------------------------+
|                      Idempotency-Key Exists in DB?                            |
+---------------------------------------+---------------------------------------+
                                        |
                   +--------------------+--------------------+
                   | YES                                     | NO
                   v                                         v
+---------------------------------------+     +---------------------------------+
|  Compare $FP_{stored}$ vs $FP_{incoming}$  |     | Begin Atomic DB Transaction     |
+------------------+--------------------+     +---------------------------------+
                   |
     +-------------+-------------+
     | Match                     | Mismatch
     v                           v
+-----------------------+   +-----------------------+
|  RETRIED_AND_MATCHED  |   |  BLOCKED_AS_CONFLICT  |
|  (HTTP 200 - Replay)  |   |  (HTTP 409 Conflict)  |
+-----------------------+   +-----------------------+
```

## 4. Status Lifecycle Engine

Each `IdempotencyRecord` follows an explicit state machine:

```
[ Incoming Request ] ---> (Validate Key & Calculate Fingerprint)
                                   |
                                   v
                             [ PROCESSING ]
                                   |
                  +----------------+----------------+
                  |                                 |
                  v (On Success)                    v (On Unhandled Exception)
             [ COMPLETED ]                     [ FAILED ]
```

1. **`PROCESSING`**: Inserted immediately inside an atomic transaction boundary to claim the idempotency key lock.
2. **`COMPLETED`**: Updated upon successful creation of the `Order` record, storing `response_code` (201) and JSON `response_body` for replay caching.
3. **`FAILED`**: Set if order processing fails due to unhandled business errors, releasing the key or recording failure.

---

## 5. Database Uniqueness & Transaction Boundary

To guarantee concurrency safety against simultaneous race conditions (e.g. two parallel threads submitting the same key at the exact same millisecond):

1. **DB Level Constraint**: `idempotency_key` column is indexed with a `UNIQUE` constraint in SQLite.
2. **Transaction Scope**:
   ```python
   try:
       db.add(IdempotencyRecord(key=idempotency_key, status="PROCESSING"))
       db.flush()  # Forces SQLite unique index evaluation
       
       # Execute Order Creation
       db.add(Order(...))
       db.flush()
       
       # Update Idempotency Record
       record.status = "COMPLETED"
       db.commit()
   except IntegrityError:
       db.rollback()
       # Re-query record created by winning thread & return idempotent replay
   ```
3. **Race Condition Protection**: If two concurrent requests hit the database simultaneously, SQLite's unique constraint forces one transaction to fail with `IntegrityError`. The harness catches this exception, rolls back, and returns the stored result of the winning transaction without creating a duplicate order.
